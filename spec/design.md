# Design

## Stack

- TypeScript everywhere. Worker entry `src/worker/index.ts`; shared
  protocol code in `src/shared/` (used by the Worker, the browser and the
  CLI); browser app in `src/ui/` bundled with esbuild into a generated
  module `src/worker/ui.gen.ts` (`export default { html, js, css }`) that
  the Worker serves at `/app.js`, `/app.css` and, as `index.html`, at the
  app's own routes (`/`, `/login`, `/signup`, `/thread`, `/compose`,
  `/requests`, `/approvals`, `/contacts`, `/settings`, `/oauth/authorize`;
  client routing). Any other unknown GET is 404 JSON. `/robots.txt` and
  `/llms.txt` are generated by the Worker (R19).
- Libraries (well-maintained, audited, pure JS, run in Workers, browsers
  and Node):
  - `@noble/curves` (Ed25519 sign/verify, X25519) and `@noble/hashes`
    (HKDF-SHA256).
  - `@hpke/core` + `@hpke/dhkem-x25519` (hpke-js) for RFC 9180.
  - `@scure/base` for base58btc (Multikey).
  - Web Crypto for SHA-256, AES-GCM, PBKDF2 and random bytes.
  - No framework in the UI: small DOM helpers, hash-free history routing.
  - Dev: `wrangler`, `vitest`, `esbuild`, `typescript`, `playwright`.

Secret: `SIGNING_SEED` = base64url of 32 random bytes
(`wrangler secret put SIGNING_SEED`). Changing it changes every user's
signing key. Local dev reads it from `.dev.vars`.

Optional var `STREAM_SECONDS` (default `"600"`): how long an MCP server
stream stays open. On the Workers Free plan a request may make 50 D1
queries, so set it to `"80"` there.

The repo keeps `wrangler.example.jsonc` with placeholders; the real
`wrangler.jsonc` with ids is git-ignored.

## Deploy

1. `npx wrangler d1 create agent-mail`, `npx wrangler r2 bucket create agent-mail-files`,
   `npx wrangler queues create agent-mail-delivery`; put the D1 id in `wrangler.jsonc`.
2. `npx wrangler d1 migrations apply DB --remote`.
3. `node -e "console.log(Buffer.from(crypto.getRandomValues(new Uint8Array(32))).toString('base64url'))" | npx wrangler secret put SIGNING_SEED`.
4. Set `SITE_URL`, `ALLOWED_EMAILS`; add a Custom Domain (`routes: [{ "pattern": "agent.example.com", "custom_domain": true }]`).
5. `npm run build && npm run deploy`. Sign up with an allowed email, choose the handle, set up encryption, download the key file.
6. Optionally set `ALLOW_SIGNUP` to `"0"` afterwards.
7. For an agent: Settings, Agents, "Add an agent"; give the agent the downloaded agent file.

Upgrading a 0.1 instance: run step 2 again (it applies
`migrations/0002_agents.sql`) and deploy. Existing tokens keep all three
scopes, get the default ask list, and lose access to account
administration; what each item's single 0.1 ack said is carried over to the
owner and to every existing token.

Two instances in the same Cloudflare zone can reach each other: a Worker's
`fetch` to another Worker's Custom Domain works. A Worker fetching its own
origin is routed internally to its own handler (see "Local delivery").

`0002_agents.sql` (0.2):

```sql
-- api_tokens is rebuilt with AUTOINCREMENT: a token id is never given to a later token.
CREATE TABLE api_tokens_v2 (id INTEGER PRIMARY KEY AUTOINCREMENT, user_id INTEGER NOT NULL, label TEXT NOT NULL,
  token_hash TEXT NOT NULL UNIQUE, created_at TEXT NOT NULL, last_used_at TEXT,
  scopes TEXT NOT NULL DEFAULT 'read send manage', ask TEXT NOT NULL DEFAULT 'first_contact policy members',
  kind TEXT NOT NULL DEFAULT 'token' /* token | oauth */, client_id TEXT);
INSERT INTO api_tokens_v2 (id, user_id, label, token_hash, created_at, last_used_at) SELECT id, user_id, label, token_hash, created_at, last_used_at FROM api_tokens;
DROP TABLE api_tokens;
ALTER TABLE api_tokens_v2 RENAME TO api_tokens;
ALTER TABLE enc_keys ADD COLUMN kind TEXT NOT NULL DEFAULT 'primary'; /* primary | client */
ALTER TABLE enc_keys ADD COLUMN label TEXT;
ALTER TABLE enc_keys ADD COLUMN token_id INTEGER; /* a client key goes away with its token */
ALTER TABLE users ADD COLUMN key_seq INTEGER NOT NULL DEFAULT 0; /* key numbers are never reused */
ALTER TABLE users ADD COLUMN doorbell_extra TEXT; /* JSON {"header-name":"value"} */
ALTER TABLE drafts ADD COLUMN sent_result TEXT;   /* set once sent: a repeated send answers the same */
CREATE TABLE approvals (id INTEGER PRIMARY KEY AUTOINCREMENT, user_id INTEGER NOT NULL, token_id INTEGER, agent TEXT NOT NULL,
  kind TEXT NOT NULL /* send | approve | block | members */, reason TEXT NOT NULL /* first_contact | policy | members | all_sends | agent_flagged */,
  ref TEXT NOT NULL /* note id, actor or thread */, subject TEXT NOT NULL /* JSON, shown to the owner */,
  payload TEXT NOT NULL /* JSON, the held call */, status TEXT NOT NULL DEFAULT 'pending' /* pending | approved | denied | cancelled | expired | failed */,
  result TEXT, created_at TEXT NOT NULL, decided_at TEXT, expires_at TEXT NOT NULL);
CREATE INDEX approvals_user ON approvals(user_id, status, id);
CREATE INDEX approvals_ref ON approvals(user_id, kind, ref);
CREATE TABLE consumers (user_id INTEGER NOT NULL, consumer TEXT NOT NULL /* 'session' or 'token:<id>' */, upto INTEGER NOT NULL DEFAULT 0, PRIMARY KEY (user_id, consumer));
CREATE TABLE consumer_acks (user_id INTEGER NOT NULL, consumer TEXT NOT NULL, cursor INTEGER NOT NULL, PRIMARY KEY (user_id, consumer, cursor));
CREATE INDEX inbox_queue_cursor ON inbox_queue(user_id, cursor);
INSERT INTO consumer_acks (user_id, consumer, cursor) SELECT user_id, 'session', cursor FROM inbox_queue WHERE acked_at IS NOT NULL;
INSERT INTO consumer_acks (user_id, consumer, cursor) SELECT q.user_id, 'token:' || t.id, q.cursor FROM inbox_queue q JOIN api_tokens t ON t.user_id = q.user_id WHERE q.acked_at IS NOT NULL;
CREATE TABLE oauth_clients (client_id TEXT PRIMARY KEY, name TEXT NOT NULL, redirect_uris TEXT NOT NULL /* JSON array */,
  source TEXT NOT NULL /* registered | metadata */, created_at TEXT NOT NULL, fetched_at TEXT NOT NULL);
CREATE TABLE oauth_codes (code_hash TEXT PRIMARY KEY, user_id INTEGER NOT NULL, client_id TEXT NOT NULL, client_name TEXT NOT NULL,
  redirect_uri TEXT NOT NULL, challenge TEXT NOT NULL, scopes TEXT NOT NULL, ask TEXT NOT NULL, expires_at TEXT NOT NULL);
CREATE TABLE oauth_tokens (access_hash TEXT PRIMARY KEY, refresh_hash TEXT NOT NULL UNIQUE, token_id INTEGER NOT NULL, client_id TEXT NOT NULL,
  access_expires_at TEXT NOT NULL, refresh_expires_at TEXT NOT NULL,
  rotated_at TEXT /* set when the refresh token was used; seeing it again ends the grant */);
CREATE INDEX oauth_tokens_token ON oauth_tokens(token_id);
```

Queue positions: a consumer has acked every item with `cursor <= upto`,
plus the cursors listed for it in `consumer_acks`. `inbox_queue.acked_at`
is no longer read. A new token's `upto` is the user's largest cursor at
that moment.

An OAuth grant is an `api_tokens` row of kind `oauth` whose `token_hash`
is a value no bearer can hash to; its access and refresh tokens are rows
in `oauth_tokens`, stored hashed. An access token counts only while its
row is not rotated and its grant row exists with the same `client_id`. A
used refresh token's row is kept with `rotated_at` set until it expires,
so that a second use is recognised; a new pair is inserted only by a
statement that also checks the grant exists.

A sent draft is kept for one hour with `sent_result` set (the JSON answer;
`'sending:<time>'` while the first call runs, taken over by another call
when it is more than a minute old), so that a repeated send for the same
Note answers from it. One send is one `DB.batch`: the thread row, the
sender's `messages` row, one `deliveries` row per recipient, attachment
grants, allow rules and the draft's `sent_result`. Queue messages are sent
after it commits. An approval being carried out has status `approving`
with `decided_at` = when it was claimed; after two minutes it can be
claimed again. `drafts.seq` is the provisional number from
prepare; the real `am:seq` is taken from `seqs` when the message is sent
(`INSERT ... ON CONFLICT DO UPDATE SET last = last + 1 RETURNING last`).

Requests are `messages` rows with `direction='in'` and `state='request'`.
A sent message is one `messages` row (`direction='out'`, `activity` = the
Create with the sender's own `am:encrypted` copy, encrypted to the sender's
key with `aad = <Note id>\n<sender actor>`) and one `deliveries` row per
recipient (the exact JSON body sent).

Doorbell bookkeeping: `doorbell_next_at` is the end of the current 30 s
window; `doorbell_pending` is 1 while a delayed `{kind:"doorbell"}` queue
message is waiting to ring at that time, so at most one is queued.

Cron (every 15 min): delete expired nonces, sessions, drafts, `rate` rows
older than 2 minutes, actor cache older than 1 day, MCP sessions idle for a
day, expired OAuth codes and refresh tokens, registered OAuth clients older
than 7 days that were never used, or not used for 90 days, and that no
grant uses; mark pending approvals past `expires_at` as `expired`; delete
decided approvals older than 90 days; queue again up to 50 deliveries that
are `queued`, never attempted and older than 10 minutes.

## Local delivery

`federatedFetch(url, init)`: when `new URL(url).origin === SITE_URL`, the
Worker calls its own fetch handler with a `Request` instead of going to the
network (no network round trip, and it works the same in local dev). The request is still
signed and goes through every inbox check. Actor lookups for local actors use
the same path.

## Owner API

All JSON. The caller is the owner (session cookie, web app) or an agent
(`Authorization: Bearer` with a connector token or OAuth access token);
401 `unauthorized` if neither. The **Who** column says who may call:
*owner* = session only (a token gets 403 `session_required`); a scope
name = the owner, or a token with that scope (else 403
`insufficient_scope`); *any* = the owner or any token. Calls marked
*held?* may answer `{"status":"pending_approval",...}` for a token (R16).

`unread`, `requests` and `latestCursor` describe the caller's own queue
position (unacked items); `unreadMessages` counts received messages the
owner has not opened and is the web app's Inbox badge; `approvals` counts
pending approvals (all of them for the owner, its own for a token). The
queue and the read state are independent: an agent acking its queue does
not mark messages read, and reading in the web app does not ack any queue.

Prepare for a reply: thread = the Note's thread; recipients = its members
minus the user. Prepare for a new thread: thread id
`SITE_URL/users/<handle>/threads/<uuid>`. `threadId` without `to` posts to
an existing thread's members. `copies` in a payload must be sealed to keys
from that recipient's `alsoKeys` (any subset, or none); in `selfPayload`,
to the user's own client keys.

## MCP server (`/mcp`)

JSON-RPC over Streamable HTTP. `POST /mcp` takes one request or
notification and answers `application/json` (no SSE on POST). Methods:
`initialize`, `notifications/initialized`, `ping`, `tools/list`,
`tools/call`, `resources/list`, `resources/read`, `resources/subscribe`,
`resources/unsubscribe`. `GET /mcp` (SSE) as in R12. `DELETE /mcp` ends the
session. Tool results are `{"content":[{"type":"text","text":"<JSON>"}],"structuredContent":<same JSON object>}`;
a failed tool is `{"content":[{"type":"text","text":"{\"error\":...}"}],"isError":true}`.

| Tool | Scope | Input | Output |
|---|---|---|---|
| `whoami` | any | | `{address, actor, encKeyId, clientKeyIds, readReceipts, agent, scopes, ask}` |
| `pull` | read | `{since?: int, limit?: 1-100}` | `{items:[{cursor,kind,sender,thread,noteId,agent,receivedAt,gapBefore,activity}], nextCursor, more}` |
| `ack` | read | `{upTo?: int, ids?: int[]}` | `{acked, unread}` |
| `list_requests` | read | | `{items:[{id,sender,thread,receivedAt,activity}]}` |
| `list_threads` | read | | `{threads:[...]}` (entries as GET /api/threads) |
| `thread_messages` | read | `{threadId, limit?: 1-500}` (default 50) | `{threadId, messages:[...]}` (entries as GET /api/threads/messages) |
| `get_message` | read | `{noteId}` | `{id,direction,type,actor,thread,activity,published,readAt}` |
| `mark_read` | read | `{noteIds: string[]}` | `{marked, receiptsSent}` |
| `fetch_attachment` | read | `{url,size,digest}` | `{base64}` (stored, still encrypted; max 5 MiB here) |
| `prepare_message` | send | `{to?: string[], replyTo?: string, threadId?: string}` | as prepare |
| `upload_attachment` | send | `{base64}` (already encrypted; max 5 MiB here) | `{url,size,digest}` |
| `send_message` | send, held? | `{noteId, payloads, selfPayload, attachments?, sensitive?}` | as outbox POST |
| `approve` / `block` | manage, held? | `{actor}` | `{moved}` / `{dropped}` |
| `change_members` | manage, held? | `{threadId, add?, remove?}` | `{members}` |
| `list_approvals` | any | `{status?: "recent" | "pending"}` | as GET /api/approvals |
| `cancel_approval` | any | `{id}` | `{id,status:"cancelled"}` |

`serverInfo` is `{name, title, version}` with `name` = `app_name`
lower-cased with dashes. Annotations: the read tools are `readOnlyHint`;
`block` is `destructiveHint`; `send_message`, `change_members` and
`mark_read` are `openWorldHint` (they reach other people); `ack`,
`send_message`, `mark_read` and `cancel_approval` are `idempotentHint`.

## Key file

```json
{"type":"agent-mail-key","v":1,"address":"david@agent.example.com","actor":"https://agent.example.com/users/david",
 "keyId":"https://agent.example.com/users/david#enc-1","privateKey":"<base64url 32 bytes>","publicKey":"<base64url 32 bytes>"}
```

Downloaded as `<handle>@<host>.agent-mail-key.json`. Anyone with it can read
the user's messages: keep it like a password.

## Agent file

What "Add an agent" downloads: everything one agent needs, in one JSON.

```json
{"type":"agent-mail-agent","v":1,"url":"https://agent.example.com","token":"am_<base64url 32 bytes>","name":"Claude Code",
 "keys":[<key file>, ...]}
```

`keys` holds the agent's own client key (its `keyId` is the client key's
id) and, if the owner ticked it, the owner's key. Downloaded as
`<name>.agent-mail-agent.json`. It is not shown again.

## CLI and local MCP server (`cli/agent-mail.mjs`)

Node 20+, one file, bundled by `npm run build:cli` from `cli/src/bin.ts`
(the bundle is committed; CI checks it matches its source). The root
`package.json` names it as `bin`, so `npx github:<owner>/<repo> <command>`
runs it; `cli/package.json` publishes the same file to npm.

Settings from the environment: `AGENT_MAIL_CONFIG` (an agent file: a path,
or the JSON itself), or `AGENT_MAIL_URL`, `AGENT_MAIL_TOKEN` and
`AGENT_MAIL_KEY` (key file paths, comma-separated, or the JSON itself).
`AGENT_MAIL_NAME` overrides the agent's name. `AGENT_MAIL_FILES` (default
`./agent-mail-files`) is the one folder the local MCP server reads
attachments from and saves them to; a path that resolves outside it is
refused. A file that is an Agent Mail key or agent file is never attached,
by the server or by the commands. It talks to `/mcp`, and to
`/api/attachments` for uploads and large downloads.

Commands (each prints JSON): `whoami`, `pull [--since N] [--limit N]`
(pull + decrypt), `ack <upTo>`, `threads`, `thread <threadId> [--limit N]`,
`requests`, `save <noteId> <index> <outfile>`, `read <noteId>...`,
`send --to a@b,c@d [--subject S] [--attach file]... [--sensitive] <text>`,
`reply <noteId> [--attach file]... [--sensitive] <text>`,
`approve <actor>`, `block <actor>`,
`members <threadId> [--add a@b]... [--remove a@b]...`,
`approvals [--pending]`,
`watch [--exec CMD] [--once] [--interval SECONDS]`, `mcp`, and
`attachment <url> <size> <digest> <key> <iv> <outfile>`.

`watch` reads `inbox://unread`, subscribes, holds the server stream open
(reopening it when it ends) and also checks every `--interval` seconds
(default 60). It fires when the latest unacked cursor grew and there is
unread mail, when the request count grew, or when the count of pending
approvals fell. Without `--exec` it prints one JSON line of counts; with
it, it runs the command (counts in `AGENT_MAIL_UNREAD` and
`AGENT_MAIL_REQUESTS`) and waits for it.

`mcp` serves MCP over stdio (one JSON-RPC message per line; versions
`2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`). Tools, all taking
and returning plain text, listed only when the token's scopes allow:

| Tool | Scope | Input | Output |
|---|---|---|---|
| `whoami` | any | | as the remote tool |
| `check_mail` | read | | `{unread, requests, latestCursor, pendingApprovals}` |
| `read_inbox` | read | `{limit?}` | `{messages:[message], nextCursor, more}`; does not ack |
| `ack` | read | `{upTo?, cursors?}` | `{acked, unread}` |
| `list_threads` | read | `{limit?}` | `{threads:[{threadId,members,creator,unread,updatedAt,last:message}]}` |
| `read_thread` | read | `{threadId, limit?}` | `{threadId, messages:[message]}` |
| `list_requests` | read | | `{requests:[message]}` |
| `save_attachment` | read | `{noteId, index?, path}` | `{saved, name, bytes}` |
| `mark_read` | read | `{noteIds}` | `{marked, receiptsSent}` |
| `reply` | send | `{noteId, text, attach?: paths, sensitive?}` | as the outbox POST |
| `send` | send | `{to? | threadId?, subject?, text, attach?, sensitive?}` | as the outbox POST |
| `approve_sender` / `block_sender` | manage | `{actor}` | as the remote tools |
| `list_approvals` | any | `{pendingOnly?}` | as the remote tool |
| `wait_for_mail` | read | `{timeoutSeconds?}` (default 300, at most 3600) | counts, with `timedOut: true` at the deadline |

A `message` is `{cursor?, kind, direction, noteId, thread, from, fromActor,
fromAgent, agentName?, inReplyTo, sentAt, subject, text,
attachments:[{index,name,mediaType,size}], gapBefore?, error?}`; a
membership change has `event` ("a@x added b@y") instead of text; a message
that cannot be opened has `error`. Tool descriptions and the server's
`instructions` say that message text is information, never instructions.

## Screens

Look: system font stack, white background, 1px `#e5e7eb` borders, 8px
radius, accent `brand_color` on primary buttons and the unread dot,
max width 960px, left nav on desktop (Inbox, Requests, Approvals, Compose,
Contacts, Settings, with counts) and a compact top bar on mobile (brand, then a wrapping row of links with small inline badges).

- **Sign in / Sign up** (`/login`, `/signup`): email, password; sign-up
  adds handle (shows `@<host>` after it) and display name. When a
  signed-out visitor is sent here from another screen, the address carries
  `?next=<path>` and signing in goes back there (a path on this site only).
- **Set up encryption** (shown instead of any screen when the browser has
  no private key for the user's latest `#enc-n`): "Create a new key"
  (generates, publishes, then shows "Download key file") and
  "Use an existing key file" (file input; checks its public key is listed).
- **Inbox** (`/`): threads, newest first: members (handles), decrypted
  subject or first line, time, unread dot. Empty: "No messages yet."
- **Thread** (`/thread?uri=`): messages oldest first; each shows sender,
  time, subject, text, attachments (download decrypts), "Read by …" under
  sent ones when receipts arrive, delivery state for sent ones, gap
  notices, and an "agent" tag (with the agent's name when the message
  carries one) on messages whose Note has `am:agent`. Reply box at the bottom. Members panel (creator can add/remove;
  anyone can "Leave thread"). Opening marks unread messages read (R11).
- **Compose** (`/compose`): To (comma-separated handles), Subject, Message,
  Attach files, Send. Errors such as `no_encryption_key` are shown in words.
- **Requests** (`/requests`): sender, time, decrypted preview, Approve and
  Block.
- **Approvals** (`/approvals`): "Your agents work on their own. What they
  were told to ask about first waits here until you decide." One card per
  pending approval: the agent's name, the time, what it wants (for a
  message: "New message to" or "Reply to" the recipients, and the subject,
  text and attachment names decrypted in the browser; for the others, the
  sender or the member change), the reason in a sentence, Approve and
  Deny. Approving a message asks for the recipients' keys, seals the text
  that is shown again for each of them in the browser, and submits that;
  when the browser cannot open the agent's copy, Approve is disabled and
  the card says so. A failure to carry it out is shown on the card. Empty: "Nothing is
  waiting for you." Below, "Recently decided": agent, kind, outcome, time.
- **Contacts** (`/contacts`): rules table, add an actor or `domain:host`
  as Allow or Block, remove.
- **Settings** (`/settings`): your address; display name; "Send read
  receipts" switch; encryption keys (download key file, create new key,
  remove old keys); doorbell URL, header name, header value (with a note
  that the value field takes only the value, for example "Bearer …", and
  that a full header line is also accepted), extra headers (a text area,
  one `Name: value` per line; shows which names are set, "Remove extra
  headers"), "Send test ring"; **Agents**: each token or connected app
  with its scopes, what it asks first, its key id, when it was last used,
  and Revoke (with a confirmation); "Add an agent": name, "It may"
  (Read mail; Send and reply; Approve or block senders, change group
  members: the first two ticked), "It asks you first before" (Messaging
  someone new; Approving or blocking a sender; Changing group members;
  Every message: the first three ticked), "Give it its own key" (ticked)
  and "Also give it my key". Adding makes the token, publishes the key and
  shows "Download agent file" and the token, once.
- **Connect an app** (`/oauth/authorize`): a centred card: "<name> wants to
  connect to the inbox of <address>.", where the browser will be sent
  back, that the app receives ciphertext unless it also holds a key, the
  same "Let it" and "It asks you first before" choices, Allow and Deny,
  and "You can revoke it at any time under Settings, Agents." A request
  that cannot be used shows why and offers nothing to click.

## Tests

- `tests/vectors.test.ts`: every vector in `test-vectors.json` (Vitest,
  plain Node; no Worker runtime needed).
- `tests/activity.test.ts`: activity validation (R9 shapes, member caps,
  addressing).
- `tests/doorbell.test.ts`: doorbell header and value normalization and
  the extra-headers parser (R13).
- `tests/client.test.ts`: sealing to several keys: every listed key opens
  the message, no other key does, and a copy is bound to its recipient (R18).
- `e2e/e2e.ts` (`npm run e2e`): builds the UI, starts two `wrangler dev`
  instances (ports 8787 and 8788, separate `--persist-to` dirs,
  `ALLOW_HTTP_LOCALHOST=1`, `TEST_ROUTES=1`), and runs `e2e/suite.ts`,
  `e2e/agents.ts` and then `e2e/ui.ts` against them. The suite covers R4-R13 over HTTP and MCP;
  every R6 row is exercised over the network (T5 forged signature, T6
  replay, T7 the remaining rows, T8 block, T9/T9b group rules), not in
  unit tests. `e2e/ui.ts` is a Playwright (Chromium) pass over the web app
  that writes the screenshots.
- `e2e/agents.ts`: the agent plan (R12-R19): T14 MCP conformance and
  discovery files, T15 what a token cannot do, T16 approvals, T17 a queue
  per agent, repeated sends and the agent marker, T18 client keys, T19
  OAuth, T20 doorbell extra headers, T21 the unattended loop (a doorbell
  ring, then an agent with only its agent file pulls, decrypts, replies
  and acks, and is held on a first contact).
- `e2e/cli-smoke.ts` (`npm run e2e:cli`): one local instance; the CLI
  commands as subprocesses, `watch --once`, and `agent-mail mcp` driven
  over stdio.
- `e2e/live.ts`: the same suites and UI pass against two deployed instances
  (`AM_A`, `AM_B` origins; `AM_PROBE` the probe key file).
- The browser pass launches the Chromium that Playwright installed, or the
  binary named in `E2E_CHROMIUM`.

### Test-only routes

When the var `TEST_ROUTES` is `"1"` (never on a real instance) the Worker
also serves:

- `GET /__test/probe`: a stand-in remote actor (no inbox) whose Ed25519
  `#sig-1` key is the Multikey in the var `TEST_PROBE_KEY`. The tests hold
  the matching private key and use it to send hand-built signed requests
  for the R6 rows (forged, replayed, stale, wrong digest and so on).
- `POST /__test/sink`, `GET /__test/sink`, `DELETE /__test/sink`: a
  doorbell target. A POST stores the body and the SHA-256 of each header
  named in `?header=a,b` (never the values; `headerSha256` is the first)
  in R2 under `sink/`; GET lists them; DELETE clears them.
- `GET /__test/oauth-client`: an OAuth client id metadata document whose
  `client_id` is its own URL.

## Deploy notes from the reference deployment

- Two Workers in the same zone with Custom Domains reach each other with
  plain `fetch` (no 522 or loop errors); the live suite passed on that
  setup.
- The reference deployment used D1, R2 and Queues on an account that
  already had Queues available; no other paid features are used.
